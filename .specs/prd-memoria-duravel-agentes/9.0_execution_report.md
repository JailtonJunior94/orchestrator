## Suposições
- O bastão de continuidade (`durable.ContinuityHandoff`/`HandoffLease`) das tarefas 1.0–7.0 é estado em memória de processo (campo não exportado em `Facade`), sem persistência em disco — correto para o uso durante uma sessão orquestrada de vida curta. Para `memory handoff` funcionar entre invocações de CLI separadas (processos distintos), o comando persiste o `HandoffLease` resultante em um arquivo sidecar JSON (`<tasks-dir>/memory/MEMORY.handoff.json`), reaproveitando `durable.LeasePolicy.Claim/Renew` (política stateless, colaborador de granularidade total, uso legítimo per MD-001) sem reimplementar a regra do lease. Nenhum arquivo da fatia 4.0 foi alterado; a persistência do lease para a superfície humana é responsabilidade nova, adicionada em `cmd/ai_spec_harness/memory.go`.
- A migração (RF-33) opera apenas sobre a camada PRD (`.specs/<prd>/memory/MEMORY.md`), que é o único caminho onde o formato legado de `internal/runtime/memory/store.go` (`WriteModeReplace`, template de 4 campos) existe hoje. A camada de projeto e a de task nunca tiveram formato legado, então não são alvo de `migrate`.
- Detecção de "já migrado" usa `PageHeader.FormatVersion != 0` após `Page.Parse` do conteúdo bruto: o formato legado nunca produz frontmatter YAML, então `FormatVersion` fica em zero-value; qualquer página já convertida pelo harness sempre grava `format_version: 1`. Heurística determinística e sem falso positivo dentro do universo de formatos que o próprio harness produz.

## Riscos Residuais
- O sidecar `MEMORY.handoff.json` do handoff via CLI é um mecanismo de persistência paralelo ao lease em memória usado pela `Facade` durante uma sessão orquestrada (`task-loop`). Os dois nunca colidem fisicamente (arquivos distintos, um por sidecar vs. campo em memória do processo do runtime), mas também nunca se enxergam: reivindicar o bastão via `memory handoff claim` não impede uma sessão orquestrada concorrente de também reivindicá-lo via `Facade.RecordSession`, porque são dois relógios de lease independentes. Isso é uma lacuna de produto pré-existente na arquitetura entregue pelas tarefas 1.0–7.0 (o lease do runtime nunca foi desenhado para ser consultável por um processo externo) e está fora do escopo de 9.0 corrigir — registrado aqui para uma futura revisão de MD-003 caso o produto precise unificar as duas fontes de verdade do bastão.
- `runCompact` tem cobertura de 52% porque o teste da tarefa exercita apenas o caminho de arquivamento bem-sucedido; o ramo `ErrLimitUnreachable` (RF-37, ausência de teste dedicado nesta tarefa) já está coberto indiretamente pelos testes de `durable.CompactionPolicy` na tarefa 3.0 (`compaction_policy_test.go`), então o comportamento subjacente está testado, apenas não o caminho de impressão de aviso no CLI.
