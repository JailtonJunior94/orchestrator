## Histórico de Revisão Adversarial

A tarefa pediu invocação de `review`. Dado o caráter de segurança do componente (gate que decide bloqueio de `git push`/`reset --hard`/etc.), cada rodada de review recebeu instrução explícita para tentar ativamente quebrar o classificador, e cada rodada encontrou um bypass real, corrigido antes da rodada seguinte:

1. **REJECTED** — separadores compostos `&&`/`||` não reconhecidos (`shlex` com `punctuation_chars=True` funde runs de pontuação contígua em um único token, que não batia com o conjunto fixo `{";", "&", "|", "(", ")"}`). Corrigido com regex `^[;&|]+$`.
2. **REJECTED** — a regex do item 1 não cobria tokens que fundem separador a parênteses (`&(`, `;(`, `)&`, `)|`). Corrigido generalizando: qualquer token 100% composto de caracteres do próprio conjunto de pontuação do `shlex` (`();<>|&`) é separador.
3. **REJECTED** — (a) aspa não fechada fazia o tokenizer engolir a exceção e devolver lista vazia -> `exit 0` silencioso; corrigido propagando a exceção como falha do classificador, tratada como fail-closed no wrapper bash. (b) Expansão de variável (`${IFS}`, `$VAR`) não coberta pelo guard de conteúdo dinâmico (que só olhava `$(`/crase); corrigido ampliando para qualquer `$` na string do comando.
4. **REJECTED** — (a) só `env`/`command` eram reconhecidos como wrapper transparente; `exec`, `time`, `nohup`, `sudo`, `nice`, `timeout` etc. escapavam por completo. (b) Continuação de linha `\<newline>` quebrava o casamento literal do subcomando (`git \<newline>push` virava token `"\npush"`). Corrigido: lista de wrappers transparentes ampliada + normalização de `\<newline>` antes de tokenizar.
5. **REJECTED** — a correção do item 4a parava no PRIMEIRO token "git" encontrado dentro do segmento do wrapper; `sudo -u git -- git push --force` escapava porque o primeiro "git" era o valor do argumento `-u` (nome de usuário), não o comando real, e o classificador desistia ali. Corrigido: para segmentos que começam com wrapper, TODAS as posições do segmento são candidatas, não só a primeira ocorrência textual de "git".
6. **APPROVED** — revisão adversarial focada (múltiplos candidatos "git" falsos antes do real, wrapper aninhado, assignments + wrapper + git real) não encontrou bypass residual. Achado `[LOW]` registrado como risco residual aceitável (ver "Riscos Residuais").

Cada rodada gerou caso(s) de regressão correspondente(s) em `scripts/test-validators.sh`, hoje 105 asserções verdes nesta seção do arquivo.

## Suposições
- `auto_push: true` remove tanto `push` quanto `push --force` do escopo (o contrato só tem um campo `AutoPush`, sem distinção de force); risco residual documentado abaixo.
- A classe de interpretador dinâmico (RF-24) se aplica a qualquer comando que contenha `eval`, `sh -c`/`bash -c`/`zsh -c`/`dash -c`/`ksh -c`, `$(...)`, crase ou qualquer `$` — não apenas quando "git" é textualmente visível — porque o ADR argumenta que esse conteúdo não é resolúvel por análise estática em nenhum caso.
- Ausência de `python3` no host faz o gate falhar fechado (todo comando exige `GOVERNANCE_INTERPRETER_OPERATION_CONFIRMED=1`), coerente com a postura fail-closed do ADR-003, mas mais restritivo que o "ok" que `doctor.checkHookInterpreter` reporta hoje para ambientes só-`jq` — risco residual documentado abaixo.
- Para segmentos que começam com um wrapper transparente de execução (`sudo`, `exec`, `time`, `nohup`, `nice`, `timeout`, ...), o classificador testa TODAS as posições do segmento em busca de um "git" real, em vez de tentar reconstruir a gramática exata de flags de cada wrapper (tarefa sem limite, avaliada e descartada durante a rodada 5 de revisão). Isso fecha o bypass por posição de argumento, mas introduz um trade-off documentado abaixo.
- `.agents/scripts/validate-task-evidence.sh` e `.agents/scripts/validate-review-evidence.sh` estão sendo editados por tarefas concorrentes (5.0/7.0) no mesmo working tree; o drift reportado por `check-scripts-sync` referente a esses dois arquivos não pertence a esta tarefa e não foi tocado.

## Riscos Residuais
- `git clean` só é classificado como destrutivo quando há `-f` (ou `--force`) combinado com `-d` ou `-x` em qualquer token de flag curta — `git clean --force --dry-run` sem `-d`/`-x` não é interceptado; não coberto pela matriz de testes desta tarefa (risco menor: sem `-d`/`-x` o `clean` não remove diretórios nem arquivos ignorados).
- `git restore --staged <arquivo>` é classificado como destrutivo do mesmo jeito que `git restore <arquivo>` — simplificação deliberada, já que o escopo mínimo da User Story só exige interceptar `git restore .`.
- Em host sem `python3`, o gate git passa a tratar **todo** comando como pertencente à classe de interpretador dinâmico (fail-closed total), postura mais restritiva que o "ok (jq disponível)" hoje reportado por `internal/doctor/doctor.go:checkHookInterpreter` — nenhuma alteração foi feita em `doctor.go` porque o comportamento fail-closed é correto pela ADR, mas fora do escopo declarado desta tarefa para alterar o texto do check.
- `make check-scripts-sync` pode reportar drift em `validate-task-evidence.sh`/`validate-review-evidence.sh` enquanto tarefas concorrentes (5.0/7.0) não commitarem seu próprio trabalho no mesmo working tree — não pertence a esta tarefa.
- `ai-spec hookaudit append` depende do binário `ai-spec` atualizado estar no PATH; a chamada é best-effort (`|| true`) e não bloqueia o gate — verificado com binário local reconstruído.
- **[LOW], achado da rodada 6 de revisão, aceito como dívida não bloqueante**: dentro de um segmento que começa com wrapper transparente, o classificador testa TODAS as posições do segmento como candidatas a "git" — isso corrige o bypass por posição de argumento (`sudo -u git -- git push`), mas pode gerar falso positivo quando "git" aparece como dado textual dentro do comando real do wrapper (ex.: `sudo -u alice -- echo git commit message` seria bloqueado, mesmo sendo um `echo` inofensivo). Esse comportamento é herdado do desenho heurístico do classificador (que já tratava "menção textual" como permitida SOMENTE fora de contexto de wrapper) e é uma troca deliberada de fail-closed sobre fail-open dentro da classe de wrapper, consistente com a postura geral da ADR-003. Não há caso de teste cobrindo esse FP específico nesta entrega; registrado para eventual refinamento futuro (ex.: restringir a varredura ao primeiro segmento não-flag após o wrapper mais próximo, com fallback fail-closed só quando a posição não puder ser determinada).
